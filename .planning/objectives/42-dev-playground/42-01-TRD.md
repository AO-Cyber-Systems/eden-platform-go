<objective>
Seed a demo tenant a developer can actually be: a company, a user, a membership, and a
role binding that grants real permissions.
</objective>

<why_coherence_matters>
The point of the playground is that authorization behaves EXACTLY as in production.
A user with no membership, or a membership with no role, produces authorization failures
that teach a developer the wrong model. The seeded tenant must satisfy the same invariants
a real signup would produce.
</why_coherence_matters>

<execution_context>
@~/.claude/devflow/workflows/execute-trd.md
</execution_context>

<constraints>
- Build tag (e.g. `//go:build dev`) so this cannot enter a production binary. An env var
  or config flag is NOT sufficient — those get set by accident.
- Idempotent: safe to call on every start.
- Use the EXISTING devstore seeding helpers. Do not add new mutation paths to devstore.
- Real password hash via auth.NewPasswordHasher — not a placeholder string.
</constraints>

- `go build ./... && go vet ./...` green with and WITHOUT the dev build tag
- `go test ./cmd/eden-platform-dev/... -count=1 -race` green
- A test proves the seeded user is a member of the seeded company AND holds a role
  granting at least one permission
- A test proves running the seed twice produces one tenant, not two
- `grep -rn "eden-platform-dev" platform/` returns NOTHING
</verify>
